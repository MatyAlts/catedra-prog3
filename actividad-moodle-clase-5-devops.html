🔗 Clase 5 – Red interna, base de datos y prácticas de desarrollo 🗄️

⏱️ Tiempo estimado: 115 minutos (Videos: 18 min + Lectura del apunte: 42 min + Actividades y verificación: 55 min)


En la Clase 2 vimos que Docker puede dejar un puerto abierto aunque el firewall diga lo contrario. Esta clase es la respuesta a ese problema: la red interna, un espacio de comunicación entre contenedores al que internet no llega.

Vas a incorporar PostgreSQL como tercer servicio, accesible únicamente desde la API y sin ningún puerto publicado hacia afuera, y vas a darle persistencia a la aplicación guardando el historial de operaciones. La clase cierra con las prácticas que sostienen el trabajo después del despliegue: gestión de la configuración mediante variables de entorno, lectura de registros (logs) para diagnosticar y una introducción a la integración continua.

📌 Temas que abordaremos:

  • Por qué existe una red interna: origen y diseño
  • Quién ejecuta el código: navegador del visitante frente a procesos del servidor
  • Anatomía de la red interna entre contenedores
  • Incorporación de PostgreSQL como tercer servicio
  • El historial: persistencia de las operaciones
  • Despliegue y verificación del aislamiento
  • Prácticas de desarrollo en el repositorio
  • Integración continua
  • Lo que este despliegue todavía no tiene

⚠️ Antes de esta clase: el front-end y la API tienen que estar desplegados y funcionando bajo tu dominio con HTTPS (Clase 4). Acá se agrega un tercer servicio sobre ese despliegue: si la base no está andando todavía, no hay dónde apoyarla.

🔥 Acá está el concepto que ordena toda la clase, y conviene que lo tengas claro antes de tocar nada: la calculadora no puede usar la red interna. El código que pide los datos corre en el navegador del visitante, que está en la casa de esa persona, no dentro de tu servidor. Por eso la API tiene que quedar expuesta a internet sí o sí. La red interna sirve cuando el que llama es otro proceso del servidor: la API hablándole a la base de datos. Ahí sí, y solo ahí, el puerto no se publica nunca.

🔑 La cadena de conexión no se escribe en el código ni se sube al repositorio. Viaja como variable de entorno del servicio. Un usuario y una contraseña commiteados en GitHub quedan en el historial para siempre, aunque después los borres.

🧪 Los valores que vienen del usuario nunca se pegan dentro de una consulta. Se pasan como parámetros y es la biblioteca la que se encarga. Concatenar texto para armar SQL es la puerta de entrada más antigua y más explotada que existe.

La verificación de esta clase no es que el historial se vea: es que la base no responda desde afuera del servidor. Comprobá las dos cosas, en ese orden.
